**Historical Baseline:** 1 January 1955  
**Technology Horizon:** At least 2026, extensible beyond

## 1. Purpose

This document converts the stable `CMD-SCH-01` to `CMD-SCH-08` and `CMD-INT-01` to `CMD-INT-13` acceptance definitions into repeatable fixture requirements. It is intended to let a future simulation test harness run the same scenarios against the domain owners and shared contracts.

This is a test-data contract, not runtime implementation or evidence that any test passes. Fixture values and identifiers below are synthetic and exist only to make tests deterministic. They are not historical claims, balance recommendations, canonical catalogue values or defaults for live simulation.

A test is **defined** when its fixture and assertions are documented, **implemented** when an executable test exists, and **passing** only when a recorded run demonstrates the assertions against the integrated runtime.

## 2. Shared deterministic test conventions

### 2.1 Fixture namespace

Use a dedicated test namespace so fixture entities cannot collide with scenario or production records. The following readable IDs are aliases for stable IDs generated by the test harness:

| Alias | Fixture entity |
|---|---|
| `NAT-A` | Test nation A |
| `HQ-A` | Issuing headquarters |
| `UNIT-A` | Subordinate company |
| `UNIT-B` | Second recipient unit |
| `CHAR-CMD-A` | Officer Character assigned to HQ-A |
| `END-HQ-A` | HQ communications endpoint |
| `END-UNIT-A` | UNIT-A communications endpoint |
| `END-UNIT-B` | UNIT-B communications endpoint |
| `ORDER-A1` | Initial order |
| `ORDER-A2` | Explicit superseding order |
| `PLAN-A1` | Initial command plan |
| `TASK-MOVE-A1` | Movement task requested by UNIT-A |
| `DEMAND-A1` | Unit sustainment demand |
| `SHIP-A1` | Supply shipment |
| `STOCK-TXN-A1` | Source reservation/issue transaction |
| `STOCK-TXN-A2` | Destination receipt transaction |
| `REPORT-A1` | Intelligence report |
| `ASSESS-A1` | Intelligence assessment |
| `EVENT-A1` | Initial causal event |

IDs in a test must remain stable across retries and save/load. A distinct operation must use a distinct ID and causation reference.

### 2.2 Time and execution

- Start each isolated fixture at simulation time `T+000`; use the simulation calendar and deterministic event ordering, never wall-clock time.
- Configure test-only delivery delays, movement durations, capacities and environmental transitions as explicit versioned fixture inputs.
- Run each scenario with a fixed seed and identical ordered inputs. If the runtime is deterministic without a seed, record that configuration.
- Execute each relevant scenario twice from a clean state and compare authoritative state and emitted events.
- For save/load tests, checkpoint at the stated in-flight boundary, reload, then continue with the same scheduled inputs.
- Assertions compare domain-owned state and event identities, not UI labels or derived display text.

### 2.3 Required event envelope assertions

For each consequential event, assert stable event ID, event type/version, source system, simulation effective time, causation/correlation reference where applicable, outcome/reason code, configuration version where relevant, and idempotency key. The physical schema may normalise these fields, but their semantics must remain testable.

## 3. Fixture A: Command order, delivery and supersession

**Covers:** `CMD-SCH-01` to `CMD-SCH-04`, `CMD-INT-02`, `CMD-INT-03`, `CMD-INT-13`.

### Initial state

- `HQ-A` has valid authority to issue order type `ORDER-MOVE` to `UNIT-A` and `UNIT-B`.
- `CHAR-CMD-A` has an effective appointment and the command authority required for the issuing role.
- All three endpoints exist. A versioned test channel has an explicit delay and delivery policy.
- `UNIT-A` has a valid standing order `ORDER-STANDING-A`.
- `ORDER-A1` is issued at `T+000`, with version 1, expiry `T+100`, and a delivery delay of 20 simulation units.
- `ORDER-A2` explicitly supersedes `ORDER-A1`, is issued at `T+010`, and has a delivery delay of 5 simulation units.

### Actions

1. Issue `ORDER-A1` without sending it.
2. Send version 1 to `UNIT-A` and `UNIT-B` as separate recipient delivery attempts.
3. Send `ORDER-A2` to `UNIT-A`.
4. Deliver `ORDER-A2` at `T+015`, then deliver the stale `ORDER-A1` at `T+020`.
5. Retry delivery of `ORDER-A2` using the original idempotency key.
6. Save/load while one recipient delivery attempt remains pending in a separate run.

### Assertions

- Issuing an order alone creates no Communications delivery record and does not mark it delivered.
- Recipient delivery states and timestamps are independent.
- `UNIT-A` validates and accepts `ORDER-A2` only if its authority, expiry and supersession checks pass.
- The later arrival of superseded `ORDER-A1` does not restore the old order or create a second actionable task.
- A retry does not create duplicate actionable tasks or duplicate delivery effects.
- `UNIT-B`'s state is not inferred from delivery to `UNIT-A`.
- Save/load resumes the pending attempt without replaying completed delivery or task-creation effects.

## 4. Fixture B: Company-to-unit sustainment

**Covers:** `CMD-INT-06`, `CMD-INT-09`, `CMD-INT-12`, `CMD-INT-13`, plus the Military Interface Audit sustainment vertical slice.

### Initial state

- `UNIT-A` has an approved, versioned physical requirement profile and an outstanding demand `DEMAND-A1`.
- Source holding `HOLD-SOURCE-A` contains eligible canonical catalogue products with explicit units, product mass, compatibility and available quantities.
- Destination holding `HOLD-UNIT-A` is associated with `UNIT-A`.
- A configured Supply Base Unit has a depot and a separate Supply Column carrier with explicit test-only handling and payload capacities.
- Government authority, Economy commercial commitment (if procurement is needed), Production execution (if replenishment is needed), Inventory, Logistics and Movement interfaces are available as separate owners.
- Route `ROUTE-A1` is feasible at `T+000`; the receiving location is accessible and has sufficient capacity.

### Actions

1. Generate and validate `DEMAND-A1`; do not reserve stock as a side effect of demand creation.
2. Request source allocation and reservation from Inventory.
3. Create `SHIP-A1` with cargo lines mapped to canonical catalogue IDs and the receiving Unit's requirement profile.
4. Load and dispatch through the authoritative Inventory and Movement transitions.
5. Advance the carrier to destination, unload, and request destination receipt.
6. Consume a defined portion of received stock using a uniquely identified authorised consumption event.
7. Replay the receipt and consumption requests using their original idempotency keys.
8. Save/load once while the shipment is in transit and once after receipt.

### Assertions

- Demand, authority, commercial order, production, stock reservation, issue, shipment, movement, arrival, unloading, receipt and consumption remain distinct transitions.
- No physical product is created from a category label, Industry Type or missing catalogue mapping.
- Source stock decreases or transfers only through Inventory-authorised transactions; in-transit cargo remains accounted for and cannot also be used as source stock.
- Movement arrival alone does not mark cargo received.
- Destination stock becomes usable only after valid receipt and compatibility/condition checks.
- Every cargo line reconciles source quantity to in-transit quantity, destination receipt, consumption and explicit loss/damage/return.
- Replayed receipt or consumption events do not duplicate stock.
- A shortage remains outstanding with a reason code; it is not silently treated as fulfilled.
- Player and AI actors obtain the same transaction constraints and conservation outcomes.

## 5. Fixture C: Blocked crossing and environmental disruption

**Covers:** `CMD-INT-01`, `CMD-INT-04`, `CMD-INT-05`, `CMD-INT-13`.

### Initial state

- `UNIT-A` has an accepted order and plan referencing route `ROUTE-A1`.
- The route contains crossing `CROSS-A`; the Movement system owns traversal and current position.
- Terrain/Infrastructure exposes a versioned crossing state. Environment exposes a versioned weather state and forecast.
- The decision-making headquarters has only the forecast/report versions delivered to it by decision time.

### Actions

1. Begin movement with the crossing open and route feasible.
2. At `T+010`, change the authoritative crossing state to blocked.
3. Emit one material-change event with stable identity and effective time.
4. In a separate run, introduce a weather change that reduces route feasibility or carrier capability under the configured model.
5. Deliver the relevant change report to `HQ-A` after a configured Communications delay.
6. Allow the next scheduled reassessment, then submit a reroute or hold request.

### Assertions

- Movement stops or interrupts at the authoritative physical constraint; the unit does not teleport through the crossing.
- Route feasibility is re-evaluated against current authoritative terrain, infrastructure, access, weather and carrier capability.
- The triggering event prompts evaluation but does not silently rewrite the order.
- Command decisions use only information available to `HQ-A` at the time of decision; the test must not give the planner the hidden future change.
- A reroute receives a new route revision or task instruction while preserving the order, shipment and cargo identities.
- Replayed obstruction/weather events do not create duplicate interruptions or reassessments with duplicate side effects.
- Save/load preserves position, route revision, interruption state and pending reassessment.

## 6. Fixture D: Command-to-intelligence information boundary

**Covers:** `CMD-INT-03`, `CMD-INT-13`.

### Initial state

- A sensor source produces observation `OBS-A1` at `T+000`; Sensors owns the observation and track.
- Intelligence produces `REPORT-A1` and `ASSESS-A1` from explicit evidence references, confidence-model version and provenance.
- Two recipient actors have different dissemination permissions.
- Communications has a configured delayed channel from the intelligence origin to each recipient.

### Actions

1. Create the observation, report and assessment with explicit source, observed, received and assessment times.
2. Queue dissemination to both recipients.
3. Deliver to one permitted recipient at `T+020`; block or withhold the other recipient according to its access decision.
4. Schedule Command reassessment before delivery and after delivery.
5. In a second run, deliver contradictory or stale evidence and create a versioned assessment update.

### Assertions

- A report/assessment does not rewrite the source observation or track.
- An assessment existing in Intelligence does not mean every actor knows it.
- Communications controls delivery timing; access policy controls eligibility.
- The commander cannot use the assessment before its delivery/availability time.
- Contradictory evidence is preserved with provenance and uncertainty; it does not silently become certainty.
- Reassessment is triggered by delivered information, not by inaccessible hidden state.
- Player and AI knowledge projections obey the same access and timing rules.

## 7. Fixture E: Combat expenditure, loss and recovery

**Covers:** `CMD-INT-06`, `CMD-INT-07`, `CMD-INT-12`.

### Initial state

- A unit has a configured weapon instance and compatible ammunition lot with explicit inventory holding.
- Combat has an authorised engagement input and versioned resolution configuration.
- Inventory owns the physical ammunition; Equipment owns weapon configuration/condition; Combat owns the engagement and expenditure result.

### Actions

1. Resolve one valid firing event `FIRE-A1`.
2. Apply the corresponding Inventory expenditure transaction.
3. Emit the combat capability/damage consequence and Logistics replenishment demand.
4. Replay the firing event and transaction request.
5. In a separate run, resolve carrier interdiction or equipment loss, then exercise recovery/capture through the appropriate owner systems.

### Assertions

- Combat resolves the engagement and reports expenditure; it does not independently decrement Inventory.
- Inventory applies the accepted expenditure once.
- Equipment condition, unit capability and Logistics demand reflect the same causal event without duplicate damage, stock loss or demand.
- Loss, capture, transfer, repair and recovery are explicit state transitions; they do not duplicate equipment or stock.
- Replaying an event has no additional physical or economic effect.

## 10. Execution evidence and release gates

Every executable run must record:

- Runtime/build identifier and source revision.
- Fixture pack version and configuration versions.
- Test ID, start state hash and ordered input/event list.
- Expected versus observed authoritative state for each assertion.
- Emitted event IDs and any rejected, deferred, unsupported or unresolved outcome.
- Save/load checkpoint and replay result where applicable.
- Final status: not implemented, blocked, failed or passed.
- Failure trace sufficient to reproduce the result.

A test must not be marked passed solely because a scenario ran without an exception. It passes only when all assertions and invariants hold.

### Military closure gates

Military may be **behaviourally specified** when canonical domain rules and ownership boundaries are stable. It may be **schema-ready** when shared logical and physical schemas, enums, ID/time primitives and migrations are agreed. It may be **integration-complete** only when:

1. Required catalogues and numeric inputs for the playable slice are approved and versioned.
2. The company-to-unit sustainment slice passes, including failure branches and stock conservation.
3. Command-to-intelligence and blocked-crossing/delayed-command scenarios pass.
4. Combat expenditure, weather disruption, communications outage and procurement/fielding boundaries pass.
5. Save/load, event replay/idempotency and Player/AI parity pass.
6. No critical ownership conflict or unresolved schema mismatch remains.

A documentation-only repository change cannot satisfy runtime gates. If the repository does not yet contain an executable simulation/test harness, report the gate as **blocked on runtime implementation**, not passed or complete.
